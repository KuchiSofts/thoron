# Upstream #1230: the "crash in `sqlite3_dbdata_init`" (2026-11-17)

ROADMAP **P5.4**. The report: Thorium 144.0.7559.254 (AVX2) on a Windows Insider build stopped once with
a breakpoint exception (`0x80000003`) in `chrome.dll`; the stack, read from the Crashpad dump without
symbols, names `chrome!sqlite3_dbdata_init+0x1516c6f` and `+0x15173c1`, `chrome!IsSandboxedProcess+0x14a82bc`,
`+0x2afa4bf`, `+0x36efa10` and `chrome!ChromeMain+0x433f9f`, under `USER32!DispatchMessageWorker`.

## What the names mean

A debugger without a program's symbols names an address after the nearest function the program
exports. Thoron 158's `chrome.dll` (the same layout as upstream's) exports five functions:

| Export | Address (RVA) | Code after it, up to the next |
|---|---|---|
| `ChromeMain` | 0x0076e3a0 | 45.4 MB |
| `GetHandleVerifier` | 0x034ca640 | 6.6 MB |
| `IsSandboxedProcess` | 0x03b58140 | 75.2 MB |
| `CrashForExceptionInNonABICompliantCodeRange` | 0x08683560 | 75.7 MB |
| `sqlite3_dbdata_init` | 0x0d23dfc0 | 61.9 MB, to the end of the code |

`sqlite3_dbdata_init` is simply the last export, so every address in the last 62 MB of the code is
named after it. `+0x1516c6f` is 22 MB further on, in some other function. Resolved with this build's
own symbols, the same offsets land in autofill and V8 code: unrelated to the report (another build has
another layout), and that is the point: the names in the report say nothing about SQLite, the sandbox
or Windows' message dispatch. The frames under `DispatchMessageWorker` only say that the stop happened
on a thread that handles window messages, such as the browser's main thread.

`0x80000003` is how Chromium ends a failed `CHECK` or a deliberate stop (`base::ImmediateCrash`), so
the crash was a check that failed somewhere in those 62 MB of code.

## Conclusion

- The root cause given in the report (SQLite's `dbdata` extension, the sandbox, the Insider build) is
  not supported by the dump: those are export names.
- The real place cannot be named from the report: upstream publishes no symbols, so the address cannot
  be turned into a function without that exact build's `.pdb`.
- For Thoron: `release.py prepare` now keeps every release's `.pdb` files (`docs/qa/CRASH_TRIAGE.md`,
  section 7), so a dump of a Thoron release can be read by function; and the stage's other condition,
  no such crash across a 48 h soak, is running (started 2026-11-17).

Checked with `chrome.dll` of the Thoron 158 AVX2 release build (158.0.8127.3010): its export table,
and `llvm-symbolizer` with its `chrome.dll.pdb`.
